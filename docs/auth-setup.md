# ตั้งค่า username/password และการผูกเครื่อง

โค้ดรองรับ username/password, LINE เปิด–ปิดโดยแอดมิน และอีเมล OTP เดิม ทุกวิธีสร้าง session ฝั่งเซิร์ฟเวอร์ บัญชีผูกได้ **1 browser profile / PWA installation ต่อผู้ใช้** ไม่ใช่การตรวจ serial number ของโทรศัพท์ หากล้างข้อมูลเบราว์เซอร์หรือเปลี่ยนเครื่อง ให้แอดมินรีเซ็ตเครื่องก่อน

## เปิดใช้งานครั้งแรก

1. สำรองฐานข้อมูล แล้วรัน `supabase/migrations/202610110001_office_auth.sql` ใน Supabase SQL Editor ไฟล์นี้เพิ่มตารางและฟังก์ชัน ไม่ลบข้อมูลพนักงานเดิม หาก LINE ID หรืออีเมลซ้ำ ต้องแก้ข้อมูลซ้ำก่อนรัน migration
2. เพิ่มค่าต่อไปนี้ใน `.env.local` บนเครื่องเซิร์ฟเวอร์:

   ```dotenv
   SUPABASE_SECRET_KEY=your_server_only_service_role_key
   LINE_LOGIN_CHANNEL_ID=your_line_login_channel_id
   APP_URL=http://localhost:3000
   ```

   ใช้ `APP_URL=https://...` เมื่อใช้งานจริง ค่า Channel ID ดูจาก LINE Developers และต้องตรงกับ channel ของ LIFF ไม่ใช่ LIFF ID ห้ามใช้ชื่อ `NEXT_PUBLIC_` กับ service role key และไม่ต้องส่งคีย์ผ่านแชต
3. สร้างบัญชีแอดมินเริ่มต้นด้วย `node --env-file=.env.local scripts/bootstrap-auth.mjs` โปรแกรมจะถาม ID ของพนักงานที่เป็น Admin และได้รับอนุมัติแล้ว จากนั้นถาม username และรหัสผ่าน โดยซ่อนรหัสผ่านขณะพิมพ์
4. รัน `npm run build` และเริ่มเซิร์ฟเวอร์ใหม่ แล้วลงชื่อผ่าน username/password
5. หน้า **แอดมิน → จัดการพนักงาน → แก้ไข** มีส่วน “บัญชีเข้าใช้งาน” สำหรับตั้ง username/password และรีเซ็ตเครื่อง พนักงานใหม่ต้องบันทึกข้อมูลก่อนแล้วเปิดแก้ไขเพื่อตั้งบัญชี
6. หน้า **แอดมิน → ตั้งค่าระบบ → วิธีเข้าสู่ระบบ** มีสวิตช์ LINE และปุ่มบันทึกของส่วนนี้ การปิด LINE ต้องมีแอดมินที่ตั้งรหัสผ่านแล้ว และจะยกเลิก session LINE ที่ใช้งานอยู่

## Token และบัญชี

- รหัสผ่านเก็บเป็น salted scrypt hash ในตารางที่ browser/anon อ่านไม่ได้
- Session token สุ่ม 256 บิต อายุ 30 วัน เก็บใน HttpOnly cookie; ฐานข้อมูลเก็บเฉพาะ SHA-256 hash พร้อมผู้ใช้และรหัสเครื่อง การออกจากระบบลบ session แต่เก็บรหัสเครื่องเพื่อให้ลงชื่อซ้ำได้
- รหัสเครื่องอยู่ใน localStorage แยกตามบัญชี ฐานข้อมูลเก็บเฉพาะ hash และใช้ transaction lock ป้องกันสองเครื่องผูกพร้อมกัน การรีเซ็ตเครื่องยกเลิก session ทั้งหมด เครื่องแรกที่ลงชื่อสำเร็จหลังรีเซ็ตจะเป็นเครื่องที่ผูกใหม่
- ลงชื่อใหม่ยกเลิก session เก่าของบัญชีนั้น เปลี่ยนรหัสผ่านยกเลิก session เดิม อีเมล OTP ไม่สามารถย้ายการผูกเครื่องได้
- LINE token ตรวจที่ LINE API ฝั่งเซิร์ฟเวอร์ รวมถึง Channel ID และอายุ token สวิตช์ LINE มีผลที่ API ด้วย
- ตาราง `office_auth_identities` เก็บ LINE/อีเมลที่แอดมินยืนยัน แก้ข้อมูลทั่วไปใน `employees` ไม่สามารถเปลี่ยนบัญชีที่ใช้ยืนยันตัวตนได้เอง การอนุมัติหรือบันทึกข้อมูลพนักงานในหน้าแอดมินจะอัปเดตการผูกนี้
- สิทธิ์จัดการบัญชีต้องมีชื่อใน `office_auth_admins` และยังมี role Admin ที่ active เมื่อเพิ่มแอดมินใหม่ ให้ผู้ดูแลฐานข้อมูลเพิ่ม `employee_id` ในตารางนี้ หรือใช้ bootstrap script สำหรับ Admin ที่ได้รับอนุมัติ
- ข้อมูล `employee_data` และ `line_profile` ในเครื่องใช้แสดงผล ไม่ใช้ยืนยันสิทธิ์ของ API บัญชีใหม่ หน้าแอปตรวจ session ตอนเปิดหน้า ทุก 60 วินาที และเมื่อกลับมาใช้งาน

การเปลี่ยนนี้ป้องกัน API ลงชื่อและจัดการบัญชีใหม่ ระบบเดิมยังมีหน้าเรียก Supabase โดยตรง ต้องตรวจ RLS ของตารางงานเดิมแยกต่างหากก่อนเปิดใช้งานภายนอก โดยเฉพาะสิทธิ์แก้ role/is_active และข้อมูลพนักงาน การใช้ service role บนเซิร์ฟเวอร์ไม่ได้เปลี่ยน RLS ของตารางเดิมโดยอัตโนมัติ

## ทดสอบ

- `npm run build`
- `node --test scripts/test-auth.cjs` ตรวจ password hashing; การทดสอบ migration ต้องติดตั้ง `@electric-sql/pglite` ใน runtime สำหรับทดสอบ และตั้ง `AUTH_TEST_PGLITE` เป็น path ของแพ็กเกจก่อนรัน
- ทดสอบรหัสถูก/ผิด, การกลับเข้าใช้หลังปิด browser, ออกจากระบบ, บัญชีรออนุมัติ, เปิดจากเครื่องที่สองแล้วถูกปฏิเสธ, แอดมินรีเซ็ตแล้วเข้าเครื่องใหม่ได้, เปลี่ยนรหัสผ่านแล้ว session เดิมถูกยกเลิก, ปิด LINE แล้วทั้งปุ่มและ API ใช้ไม่ได้ และเปิด LINE กลับได้

หากยังไม่ได้ตั้ง service role key หรือรัน migration หน้า login จะแสดงว่าระบบยังไม่พร้อม และจะไม่สร้าง session จำลอง
